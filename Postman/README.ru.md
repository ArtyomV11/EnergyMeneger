## Запуск

1. Импортируйте `EnergyMeneger.postman_collection.json` и `EnergyMeneger.postman_environment.json` в актуальный Postman с поддержкой `pm.execution.skipRequest()`.
2. Выберите environment **EnergyMeneger localhost 7080**.
3. Введите `ownerLogin` и `ownerPassword`, использованные при инициализации через `Bootstrap:Login` / `Bootstrap:Password`. Оба поля оставлены пустыми: репозиторий не содержит этих значений. Пароль владельца не генерируется. Bootstrap не создаёт начальников или рабочих.
4. Запустите приложение с настроенной PostgreSQL и JWT. База должна быть уже инициализирована. `--initialize` создаёт исходные данные один раз и завершает приложение; на существующей базе повторный запуск инициализации запрещён.
5. Запустите всю коллекцию в Runner, сверху вниз, 1 iteration. `baseUrl=https://localhost:7080`. После успешного входа токены, сроки действия и ID сохраняются автоматически. Не задавайте ID вручную.
6. По умолчанию `runWriteTests=false`: выполняются чтение и отрицательные проверки без изменения производственных настроек. Для полного сценария на тестовой базе установите `runWriteTests=true` и снова запустите всю коллекцию.

При ошибке доверия к локальному HTTPS-сертификату добавьте dev certificate в доверенные сертификаты. Для локального тестирования можно отключить SSL certificate verification в настройках Postman.

## Изменения при полном прогоне

Все изменения настроек цехов и оборудования относятся к новым тестовым объектам. Исходные цехи и шесть устройств Bootstrap не изменяются. ID находятся по исходным именам, поэтому сохраните эти имена для discovery.

Сумма исходных лимитов уже составляет 300 кВт, поэтому перед созданием цеха коллекция сохраняет текущие настройки подстанции, увеличивает её лимит на 60 кВт и создаёт отдельный EquipmentBased-цех с лимитом 60 кВт. Новый цех, сотрудники, оборудование и история остаются в БД. Вернуть лимит подстанции к исходному значению без удаления тестового цеха невозможно: это нарушит сумму распределённых лимитов. Каждый полный прогон добавляет ещё 60 кВт и новый набор объектов. Для повторяемого чистого состояния используйте отдельную тестовую БД и восстанавливайте её копию.

Финальная папка выключает тестовые устройства, блокирует тестового начальника и увольняет тестового рабочего. Увольнение необратимо через API. DELETE пользователя отсутствует. DELETE цеха после его создания возвращает 409 из-за Snapshot/истории. DELETE оборудования после переключений возвращает 409 из-за истории и логов. Это ожидаемые успешные проверки ограничений. Гарантировать успешный DELETE только что созданного оборудования нельзя: фоновый SimulationWorker может создать историю между запросами. Коллекция намеренно проверяет детерминированный 409, а не обещает успешное физическое удаление.

При прерванном прогоне на тестовой базе запустите папку 08 отдельно с тем же environment для завершения выключения и блокировки. Не начинайте новый полный прогон до этого: папка 01 обновляет временные ID. Если создание части объектов завершилось ошибкой, проверьте результаты запросов перед продолжением.

## Порядок сценариев

1. Вход владельца, уникальные логины и пароли тестовых сотрудников, очистка временных переменных.
2. Получение реальных ID исходных объектов, снимка подстанции и factoryId.
3. Проверки 401/404/400 без записи.
4. Выделение бюджета, создание и изменение тестового цеха, создание Foreman/Worker, входы.
5. Ограничения ролей и доступа к чужим цехам и оборудованию, запрет операций владельца.
6. CRUD оборудования и лимиты: Secondary 40 кВт, Important 40 кВт вытесняет Secondary, Critical 70 кВт получает 409 при лимите цеха 60 кВт. Мощности фиксированы, поэтому случайная симуляция не меняет ожидаемый результат. Worker не может переключать оборудование, Foreman может.
7. История equipment/workshop, статистика equipment/workshop/factory, summary и logs. Нулевые результаты допустимы: Bootstrap не заполняет историю задним числом.
8. Смена роли с действующим JWT, блокировка и немедленный 401, восстановление Active, увольнение и запрет повторного изменения, завершение сценария.

API ограничивает входы до 10 в минуту на IP. Один прогон выполняет 5 попыток входа; перед повтором подождите минуту, учитывая входы из браузера. Отдельного refresh endpoint нет; повторите login для нового токена (срок 2 часа). Пароли и токены помечены как secret в environment, но экспорт environment с заполненными значениями всё равно требует осторожности.

`from`/`to` устанавливаются первым запросом как UTC ISO 8601 с Z, от суток назад до минуты вперёд. При ручном запуске папки отчётов обновляйте период самостоятельно: максимум 31 день, глубина до 3 лет. Для history допустимы equipment/workshop, для statistics также factory. `page=1`, `size=100`; разрешены page 1–100000 и size 1–1000.
